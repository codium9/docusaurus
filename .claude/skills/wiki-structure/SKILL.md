# Structure du wiki Docusaurus

Le wiki (`docs/`) utilise une sidebar **autogenerated** (`sidebars.js`) : la navigation vient uniquement de l'arborescence, des `_category_.json` et du frontmatter. Il n'y a donc rien à déclarer dans `sidebars.js` ; une structure incohérente se traduit directement par un menu mal ordonné ou un dossier invisible.

## Conventions observées

- Un dossier contenant au moins une page doit avoir un `_category_.json`. Format compact : `{ "label": "Docker", "position": 3 }`. `label` = nom du dossier, `position` = ordre parmi les frères.
- Les sous-catégories peuvent ajouter `"collapsible": true, "collapsed": false, "link": null` (cas de `Kubernetes/Lexique`). Ne pas les ajouter sans demande.
- Pages en `.mdx` avec frontmatter `title`, `description`, `sidebar_position`.
- Fichiers et sous-dossiers d'un même dossier partagent la même échelle de position : éviter les doublons.

## Workflow après création ou modification de pages

1. Auditer : `python3 .claude/skills/wiki-structure/scripts/sync_structure.py docs`
   (lecture seule ; code retour 1 si une catégorie manque ou si un JSON est invalide).
2. Créer les catégories manquantes : même commande avec `--fix`. Le script ne touche jamais à un `_category_.json` existant ni aux pages.
3. Traiter les avertissements à la main, en demandant si le choix n'est pas évident : `title` ou `sidebar_position` absent, position en double, dossier sans page. Quand l'utilisateur donne l'ordre voulu, éditer les `position` / `sidebar_position` concernés ; sinon proposer un ordre sans l'appliquer.
4. Si un label doit être plus lisible que le nom du dossier (accents, espaces), l'éditer dans le `_category_.json` créé.
5. Résumer ce qui a été créé ou modifié, en une ligne par fichier.

## Limites

- Ne génère pas d'aperçu du site (retiré à la demande de l'utilisateur : l'accès au serveur depuis l'hôte WSL ne fonctionnait pas).
- Ne fait aucune opération git : l'utilisateur gère les commits.
- Ne modifie pas `docusaurus.config.js` ni `sidebars.js`.
